手头有个叫 memaudit 的小工具，用 POSIX shell 写的采集器跑在板子上，把 `/proc`、`/sys`、设备树里的内存账本抓成一个快照包，PC 端再对账出报告（"内存不见了"那类问题）。功能一直没问题，直到在一台 347 个进程的 RDK X5 上跑了一次——采集要 **8 到 10 秒**。

这篇记录一下怎么把它压到 1 秒出头的。真正有意思的不是结论，而是"慢在哪里"的答案和过程中踩的坑。

## 先量，再改

性能优化的第一步永远是测量。我给脚本加了两层探针：

**段耗时**：在采集器的 `begin()/end()` 打点处插入时间戳，每个段落（meminfo、procs、fds、dmesg……）各花多少毫秒一目了然。

**spawn 计数**：这个更关键。做一个假 PATH，把 `cat`、`tr`、`awk`、`ls` 这些命令替换成"先记一笔、再执行真身"的包装器：

```sh
printf '#!/bin/sh\nprintf "%%s\n" "%s" >> "$SPAWN_LOG"\nexec %s "$@"\n' \
    "$c" "$real" > "wrap/$c"
```

然后 `PATH=wrap:$PATH` 跑一遍，日志里就是每个外部命令被 fork 了多少次。零依赖，比任何 profiler 都直观。

结果一出来就清楚了：

| 段落 | 耗时 | 占比 |
|---|---|---|
| procs（每进程 RSS/PSS） | 713 ms | 60% |
| fds（dma-buf 句柄） | 216 ms | 18% |
| cmds（命令行） | 197 ms | 17% |
| 其余 16 个段落合计 | ~60 ms | 5% |

而 1765 次 spawn 里，光 `tr` 就 810 次、`awk` 393 次、`cat` 287 次——**每个进程约 12 次 fork**。按单次 spawn 0.46 ms 算，纯进程创建开销约 815 ms，占上面三个热段落合计耗时（约 1.19 s）的 **69%**。

## 被误解的"慢"：不是数据量

一开始我怀疑是数据太大。测了一下：读一个 2 万 VMA 进程的全量 `smaps` 只要 **60 ms**，`smaps_rollup` 更是只要 6.5 ms。数据根本不是瓶颈。

瓶颈是这句再普通不过的写法：

```sh
comm=$(cat "$d/comm" 2>/dev/null | tr -d '\012' | tr '\011' ' ')
```

一行就是 3 次 fork（`cat` + 2 个 `tr`，还没算子 shell）。每个进程再来一遍 uid、oom_score、cmdline、fd 目录……12 次 fork 就这么来的。在 x86 上 fork 便宜得可以忽略，在 Cortex-A55 + busybox 上，每次 spawn 是 1–3 ms 的真金白银。

思路因此明确：**把"每进程 N 次 fork"改成"全程常数次 fork"**。

## 四项改造

**procs 段：改用 shell 内建 `read`**。shell 内置命令不产生 fork，直接解析：

```sh
while read -r k v _; do
    case "$k" in
        Rss:) v_rss=$v ;;
        Pss:) v_pss=$v ;;
        Anonymous:) v_anon=$v ;;
    esac
done < "/proc/$pid/smaps_rollup"
```

140 个进程从 713 ms 降到 34 ms。这里有个细节：`read` 必须用**默认 IFS**——`status` 里的 `Uid:` 行是 tab 分隔，只按空格读会把整行当成一个字段。

**fds 段：一次 `ls` 扫全部**。原来是"每进程 ls + 每个 fd readlink"，现在一条命令列出所有进程的 fd 目录，`awk` 靠 `路径/fd:` 头行切分进程：

```sh
ls -l /proc/[0-9]*/fd 2>/dev/null | awk '
    /^\/proc\/[0-9]+\/fd:$/ { ...取 pid... }
    / -> / { ...取 fd 号和目标... }'
```

369 个 fd 从 216 ms 降到 6 ms。

**cmds 段：marker + 单管道整形**。把每个进程的 cmdline 拼成一条流，用标记文件切分边界，`cat | tr | awk` 三个进程搞定全部：

```sh
cat $MARGS | tr '\000\011' '\n ' | awk '
    /^###[0-9]+$/ { ...输出上一个进程...; cur = substr($0, 4); next }
    { ...拼接命令行... }'
```

**dma_maps 段：先在便宜的文件上预筛**。原来对每个进程扫全量 `smaps`；改成先扫一遍 `/proc/*/maps`（比 smaps 便宜得多）找出含 dma/mmz 映射的候选进程，再只对候选读 `smaps`。`maps` 和 `smaps` 枚举的是同一组 VMA，路径匹配等价，不会漏。

结果（同一台板子、同一负载）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| `--fast` | 8.4 s | **1.07 s** |
| `full` | 10.2 s | **1.2 s** |
| spawn 次数 | 4666 | **239** |

## busybox 的三个陷阱

这类脚本的目标环境是板子上的 busybox，不是 GNU。这次踩到的三个坑都值得记下来：

**一、busybox awk 处理不了含 NUL 的数据**。`/proc/PID/cmdline` 是 NUL 分隔的。在 mawk 上 `getline` 能完整读到含 NUL 的字符串，`gsub(/\000/, " ")` 也正常；但 busybox awk 会把 NUL 当记录分隔符拆开，而 `gsub(/\000/)` 会退化成**空匹配**——往干净字符串里插入莫名其妙的东西。结论：NUL 必须在 awk 之前先用 `tr` 归一化。

**二、procfs 的 `st_size` 是 0**。给 cmdline 判空我顺手写了 `[ -s "$d/cmdline" ]`，结果整个段落输出为空——procfs 是动态生成的，`stat` 里的 size 恒为 0，`-s` 对所有进程都判定"空文件"。只能改用 `[ -r ]`，空内容交给下游跳过。

**三、`Uid:` 行是 tab 分隔的**。这个坑最隐蔽：旧代码用 `awk -F': ' '/^Uid:/{print $2}'` 取 uid，而 `/proc/PID/status` 里是 `Uid:\t0\t0\t0\t0`——FS 是"冒号加空格"，对 tab 不匹配，所以 **uid 列一直是空值**。这个 bug 存在了很久，报告里那列全是 `?`，居然一直没人注意。

验证兼容性的一个实用技巧：busybox 官方提供**静态二进制**（单文件、可在 x86 上跑），下载下来就能在开发机上验证每个 shell/awk/tr 的写法在 busybox 下的真实行为，不用来回刷板子。

## 差分测试：比"跑一遍看输出"值钱得多

改完最怕的是"看起来对"。我的验证方法是跑**差分测试**：

1. 新旧脚本**并发**跑同一负载（同一时刻采样，天然消除系统漂移）；
2. 输出做规范化：去掉时间戳之类的易变 meta，对进程列表这类无序段落排序；
3. 跑两组，先用"同版本跑两次"的差异建立**噪声基线**，再对比新旧差异。

超出噪声基线的差异，就是真实行为变化。结果是除预期项外逐字节一致——同时还抓出三个旧版的数据 bug：

**uid 恒为 `?`**（上面第三条）。

**内核线程的行在复制邻居的内存值**。旧代码用 `eval "$(awk ...)"` 赋值，当 `awk` 读内核线程的 `smaps_rollup` 报错时输出为空，`eval` 什么都不做——**变量保留了上一轮进程的残留值**。于是每个内核线程都顶着相邻进程的内存数据，一台板子 184 行受影响，等于把邻居的内存重复计了一遍。新版每轮显式初始化变量后，这些行正确地显示为 0。

**fds 漏掉含空格的 deleted 目标**。旧匹配用 `$NF`（最后一个字段），而 `ls` 对已删除文件会显示 `path (deleted)`，最后一个字段变成了 `(deleted)`——memfd 这类目标全被漏掉。

顺带发现这类工具里一个通用规律：**内核线程没有用户地址空间，它的内存列应该是 0**；任何非 0 都值得怀疑。

## 我自己踩的坑

过程里两次低级失误也一并记下：

- 测试脚本里用 `wait` 等待两个采集进程，结果它**等上了所有后台子进程**——包括测试负载里 60 个 `sleep 600`，脚本整整卡了十分钟。要 `wait $pid1 $pid2` 精确等待。
- 清理残留进程时按 cmdline 关键字匹配，把自己的 shell 也杀了（它的命令行里就含着这些关键字），整条命令静默中断。

## 最后几条经验

- **在弱 CPU 上，fork 是最贵的操作**。同一个脚本在 x86 上 1 秒、在 A55 上 10 秒，差的不是算力而是进程创建。
- **零依赖的 spawn 计数比 profiler 更好用**。一个假 PATH 目录加几行 shell，就能把"慢"翻译成"多少次进程创建"，嵌入式环境里尤其合适。
- **差分测试能抓真 bug**。这次找出的三个数据缺陷，单看运行结果都不可能发现——只有新旧并排、基数对齐了才现形。
- **busybox ≠ GNU**。目标环境用什么，就在什么上验证；静态 busybox 二进制让这件事变得很容易。

下一步还有一段没清干净：设备树段的每个属性还要起一次 `od|tr`（板上剩余 239 次 spawn 里约 202 次是它）。换成 `hexdump -e` 单进程输出，应该还能再砍一半——下次再说。
