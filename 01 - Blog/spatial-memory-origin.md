我有一台 Pincher 机械臂，一直想让它自己去桌上把杯子拿过来。

卡住的地方不是抓取。抓取有成熟的手眼标定和 IK 方案，真正麻烦的是：机械臂转个身，杯子就不在视野里了。它不知道杯子刚才在哪，也不知道这次看到的杯子和上次是不是同一个。每次重新看见，都像第一次看见。

感知系统回答的是"这一帧里有什么"，但没有人回答"昨天看到的东西现在在哪"。我想做的就是这一层：机器人的记忆。

## 记忆不只是"存下来"

一开始我以为这件事不难，把检测结果按时间写进数据库就行。

真动手才发现，"存下来"和"记得住"是两回事。一个 ROS bag 也能存，但 bag 是用来回放的，不是用来查询的。真正需要回答的问题是这样的：

- 杯子现在在哪，置信度多少，最后一次看到是什么时候？
- 十分钟前它在哪？
- 桌上还有哪些东西？
- 这个杯子是上次那个，还是新出现的？

这些问题对应的是写入、索引、查询、一致性、淘汰。换句话说，记忆本质上是一个时空数据库。

这个判断让我踏实了一点。我本职做嵌入式存储，文件系统、索引、掉电恢复这些做了很久，只是以前存的是视频流，现在要存的是物体。领域变了，问题结构没变。

## 先看别人怎么做

方向有了，但我对机器人领域并不熟。于是花了一周读论文和开源代码，想先搞清楚"机器人记空间"这件事现在做到哪一步了。

最早看的是 SLAM 和度量建图。ORB-SLAM3、RTAB-Map 这一类，输出点云、位姿、占据栅格，导航和避障全靠它们。但它们只有几何，没有物体概念，问"杯子在哪"只能返回一堆点。这条路解决不了我的问题。

然后是语义建图。Kimera-Semantics、voxblox++ 在几何上叠类别，能回答"杯子在哪"了，给一个坐标。但我想要的是"桌上那个红色的杯子"——"在桌上"是物体间的关系，"红色"是属性，语义地图里没有独立的表示位置。

再往上是 3D 场景图，也就是 3DSG。物体是节点，关系是边。读到 Hydra 和 Kimera 的多层图时，我觉得结构是对的了。我把 Hydra 的代码拉下来看了一遍，它的四级图（建筑→楼层→房间→物体）很完整，但对我这个单房间、8GB 内存的场景来说太重了。

这里我走了个弯路。查资料的时候看到 3DGS 也很火，一度以为 3DGS 就是 3DSG 的另一种叫法，还认真研究过能不能用它做记忆。后来才分清：3DGS 是 3D Gaussian Splatting，做外观重建的；3DSG 是 3D Scene Graph，做结构和关系的。两个东西只差一个字母，方向完全不同。

## 3DSG 是什么

3DSG 的全称是 3D Scene Graph，三维场景图。结构就是一张图：

```text
节点：物体（杯子、茶几、沙发、客厅）
边：  空间关系（在…上、在…里、在…旁边）
属性：类别、颜色、置信度、首次/最后观测时间
```

还是用那个房间的例子，客厅有沙发，茶几上放着红杯子，十分钟前杯子还在厨房，存进去大概是：

```text
杯子   红色、可拿、置信度 0.9    在 茶几 上
茶几   木质                     在 客厅 里
沙发   灰色                     在 客厅 里
客厅   -                        在 房子 里
```

查询"桌上那个红色的杯子在哪"，沿着"红色 → 杯子 → 在茶几上 → 茶几在客厅"走一遍就得到结果。这种结构能直接喂给语言模型做规划，也是它这两年研究这么多的原因之一。

我记下的代表工作有四个：

| 工作 | 特点 |
|---|---|
| Kimera（MIT，2020） | 度量-语义 SLAM，多层图，C++ 开源 |
| Hydra（MIT，2022） | 实时 3DSG 构建与优化，建筑→楼层→房间→物体四级 |
| SceneGraphFusion（CVPR 2021） | 增量式 3DSG 构建 |
| ConceptGraphs（ICRA 2024） | 开放词汇 3DSG，CLIP + SAM，节点可以无限扩展 |

3DSG 变热有两个很实际的原因。一是 CLIP、SAM 让任意物体都能被检测和分割，节点不再受预定义类别限制；二是 LLM 需要结构化的世界描述才能规划，图结构正好匹配。

但论文多不代表用得多。完整的四级图构建成本很高：每帧都要检测、分割、判断关系，回环修正之后整张图还得重建。实际产品里，多数还是"度量地图 + 语义标注"，全 3DSG 的系统并不多。

所以"机器人对空间的记忆是不是都用 3DSG"，答案是否定的。导航用度量表示，大范围移动用拓扑，模糊搜索用特征，长期巡检用语义加情节。3DSG 只在需要关系推理和语言接口时占优。

## 3DGS 和 3DSG 的区别

既然混过一次，就把它记清楚。

| | 3DGS | 3DSG |
|---|---|---|
| 全称 | 3D Gaussian Splatting | 3D Scene Graph |
| 用途 | 场景外观重建、新视角合成 | 物体与关系的结构化表示 |
| 存什么 | 几百万个高斯椭球参数 | 物体节点 + 关系边 |
| 数据量 | 一个房间几百 MB 到几 GB | 几百个物体几 MB |
| 算力 | 训练需要强 GPU | CPU 可以跑 |

3DGS 解决的是"从这里看过去长什么样"，3DSG 解决的是"什么东西在哪、和谁有关系"。两者可以组合，用 3DGS 重建外观，再分割物体建图，但那是两个模块。

对 310B 来说，3DGS 可以直接排除。一个房间的高斯数据就几百 MB，四核 A55 渲染都吃力，训练更不可能。

## 发现一个空白

把这几类都过完，我画了一张三层图：

| 层 | 内容 | 代表工作 | 成熟度 |
|---|---|---|---|
| 度量层 | 点云、网格、voxel、坐标与尺度 | ORB-SLAM3、RTAB-Map | 相对成熟 |
| 语义层 | 物体、房间、空间关系 | Hydra、Kimera、ConceptGraphs | 研究中 |
| 情节层 | 带时间戳的观测事件，记忆的更新与回溯 | ReSpaceBench 相关 | 最不成熟 |

然后我注意到一件事：这三层的工作，绝大多数在解决"怎么把图建出来"，很少有人把它当成一个要长期运行、要被高频查询、要能掉电恢复的系统来做。

- 建图论文关心的是精度和召回，不是查询延迟；
- 开源的语义 SLAM 大多用 ROS bag 或一个 SQLite 应付存储；
- 长时运行之后记忆怎么衰减、怎么淘汰、怎么保持一致，讨论得很少。

2026 年有几篇论文正好戳在这个空白上，我读完之后确定了自己的位置：

**Yggdrasil（arXiv:2609.38640）** 指出，现有 3DSG 研究都在优化建图，没人管图怎么被查询，查询延迟经常超出实时预算。它用分层结构加面向消费端的索引，把查询压到 2~127µs，比传统实现快两个数量级。

**PORTER（arXiv:2609.33258）** 做端云驻留：哪些记忆留在端上、哪些换出去、哪些丢掉。91% 的物体数据卸载到云端之后，检索质量 mR@3 还是 100%。这本质上就是缓存置换和分层存储。

**ReSpaceBench（arXiv:2611.21485，Lost in the Hallway）** 是评估。590 个场景、3244 个问题、9 类任务，专门测"重访同一地点能不能认出来、物品变了能不能更新记忆"。模型侧的成绩：最强零样本 50.5%，人类 90.1%，微调 Qwen3-VL-8B 后 60.4%。这个数字说明持久空间记忆本身还远没解决。

读完这三篇，我的判断是：这个方向不缺建图的方法，缺的是把记忆当成存储系统来设计的人。而这正好是我做了很多年的事。

## 我打算做什么

一句话：给机器人做一个按对象存取的时空数据库，输入是检测框和位姿，输出是"杯子在 (0.42, -0.15, 0.78)，置信度 0.87，最后观测于 12:11"。往上可以接语言查询、导航、机械臂。

空间记忆的需求，逐条都能对上存储系统的问题：

| 空间记忆的需求 | 对应的存储问题 |
|---|---|
| 长期运行，数据持续写入 | 写放大、日志结构 |
| 毫秒级回答"杯子在哪" | 空间索引、查询优化 |
| 8GB 内存 vs GB 级点云 | 热/温/冷分层 |
| 回环后地图重投影 | 版本化数据、一致性 |
| 掉电重启不丢 | WAL、快照、恢复 |
| 物体移动后的旧记忆 | 变化检测、墓碑、衰减 |
| 多机器人共享 | 分布式一致性 |

3DSG 在这里不是必须完整实现的东西，只是数据模型的一种表达。单房间场景不需要四级结构，取它的内核就够：对象节点、关系边、可查询。关系图做成可选视图，对象表是主体，以后要加语言查询或者关系推理，不用动核心。

不做的部分也列清楚，免得做着做着跑偏：

| 做 | 不做 |
|---|---|
| 对象级存储引擎（C++20，自研索引） | SLAM 本体（用现成的给位姿） |
| 空间、时间、语义查询 | 训练检测模型（用现成 YOLO 转 OM） |
| 持久化与掉电恢复 | 3DGS、NeRF 渲染 |
| 分层存储与观测压缩 | 大模型 VLA |
| ROS2 节点接入 | 多机器人分布式（远期） |
| 机械臂联动演示 | 完整导航栈 |

功能按优先级分三档：

- P0：对象建库、半径查询 P99 < 500µs、时间查询、类别查询、WAL 持久化、可复现的基准报告。
- P1：内存/卡/归档分层、观测压缩比 > 10:1、衰减淘汰、ROS2 节点、真实摄像头接入、RViz 可视化。
- P2：关系查询、重访一致性（回环后坐标重投影偏差 < 5cm）、机械臂抓取闭环、按 ReSpaceBench 任务设计的评估。

产品形态就三样：一个 C++ 库、一个 ROS2 节点、一个 CLI 工具。

## 先验证再投入

方向定下来之后，我没有马上写完整引擎，而是先做了几个小实验。理由很实际：如果硬件撑不住，架构写得再漂亮也没用。

第一件事是验证空间索引在 A55 上能不能做到亚毫秒。我写了一个两百行的网格哈希原型，`unordered_map<uint64_t, vector<EntityId>>`，网格 1 米，塞 10 万个随机对象，跑半径 1.5 米查询。结果是 P50 14.9µs、P99 18.3µs。这个数字比我预期好，说明性能目标不是吹的，可以往下做。

第二件事是测存储。SD 卡顺序写 30.2 MB/s，4K 随机写加 fsync 是 6.13ms。这个延迟决定了 fsync 不能放在查询路径上，只能走后台批量提交。SQLite 开 WAL、每 1000 条一个事务，写入 37,857 行/秒，够用。

第三件事是 NPU。yolov10n 转成 OM 之后在板上跑 30.58ms/帧，约 32.7 FPS，640×640。检测这一环不是瓶颈。

最后一个实验跟摄像头有关。我拿公开的双目数据跑了一遍 SGBM，想先知道室内场景的深度能到什么精度，再决定要不要等硬件。结论是 720p 下够用，但没有真实标定数据，只能算预演。后来证明，摄像头本身才是整个项目里最耗时间的部分，那是另一篇的内容。

这几个数字后来都写进了 README。它们不只是性能记录，也是我决定架构的依据：索引够快，所以热点数据可以全放内存；fsync 够慢，所以持久化必须异步；NPU 有余量，所以检测和特征提取可以并行。

## 下一步

现在的计划是按 v0 到 v3 往下做：先把存储内核和基准跑出来，再补持久化和观测压缩，然后接特征检索和 ROS2。硬件这边，串口、系统、远程桌面已经跑通，摄像头还在和驱动较劲。
